I want to fine-tune a small model on my lab's papers. where do I start?

Start by deciding what the model should do better after training: answer questions about the papers, write in their style, or summarize them. The goal sets the data format.

Then pick a base model small enough to iterate quickly. A 1B model trains in days on a few GPUs, which leaves room for several attempts.

Before any training, write 30 to 50 test questions with good answers. You will use them to check every run, so write them first and do not change them afterwards.

Finally, run the base model on those questions. Its score is the baseline that fine-tuning has to beat.

what's a reasonable dataset size for fine-tuning a 1B model?

It depends on how far the task is from the base model's training data. For a new domain or style, a few hundred million tokens is a common starting point.

More data helps less than cleaner data. A smaller set with duplicates and boilerplate removed often beats a larger raw one.

Hold out a slice for validation before you look at any results, so that the numbers you report are not tuned to it.

how should I clean scraped text?

Start with exact deduplication, then near-duplicate removal with MinHash. Scraped sets often contain the same page many times under different URLs.

Then drop navigation menus, cookie banners and very short pages. A simple rule such as "at least 200 words and at least 70% letters" removes most of them.

Finally, read 50 random samples by hand. It is the fastest way to find a problem that the rules missed.

Plan a fine-tuning run for a 1B model on my dataset of 1.2M sequences.

Here is a plan you can run on 4 GPUs. Each step lists the setting and the reason for it.

1. Clean and split the data

Remove exact duplicates, then hold out 2% of the sequences for validation. Split by document, not by sequence, so that no document appears on both sides.

2. Tokenize and pack

Tokenize with the base model's tokenizer and pack sequences to 2,048 tokens. Packing avoids padding, which would otherwise waste about a third of each batch.

3. Learning-rate schedule

Warm up linearly from 0 to 2 × 10⁻⁴ over the first 2% of steps, which is 400 of 20,000. Then decay along a cosine curve to 10% of the peak.

4. Batch size

Use an effective batch of 512 sequences: 8 per GPU, 16 accumulation steps and 4 GPUs.

5. Evaluate

Evaluate on the held-out split every 500 steps, and keep the checkpoint with the lowest validation loss.

6. Log and checkpoint

Log the training loss every 10 steps and the gradient norm every 50. Save a checkpoint at every evaluation, and keep only the best three.

What to watch in the first hour

The training loss should fall steadily once warmup ends. A gradient norm that keeps rising is the earliest sign that the peak rate is too high.

which GPUs do I need for this?

Four 80 GB A100s are enough. In bf16 the weights take about 2 GB, and the optimizer's states add about 12 GB per copy of the model.

Most of the remaining memory goes to activations. A batch of 8 sequences per GPU keeps the peak under 60 GB.

how long will it take?

The run processes 20,000 × 512 × 2,048 ≈ 21B tokens. At about 25,000 tokens per second per GPU, four GPUs handle 100,000 tokens per second.

That gives about 58 hours, plus roughly 40 minutes for evaluation.

should I use LoRA instead?

Only if memory or time is tight. LoRA trains far fewer parameters and would fit on one GPU.

On a dataset this large, full fine-tuning usually reaches a lower validation loss, so I would keep the plan as it is.

Brainstorm

The problem

  • Questions come up while you read, and they point at what is on screen: "why this step?", "does this look right?".
  • The thing you mean may be above you in the same chat, in a side chat, or in a code diff next to it.
  • Today you highlight and reply, paste the code, or write "in train.py, line 39…". Each one breaks your reading.

One rule

  • The context is the pane you scrolled last, read as the text visible in it and weighted toward the middle.
  • With one chat open, that is the earlier answer you scrolled back into.
  • With a diff and a side chat open, scrolling the diff makes the diff the context, even if you then type in the main chat.
  • The answer appears where you typed.

How I behaves

  • It sends the message, in place of Enter. Enter still sends without screen context.
  • Nothing appears in the interface: no logo, chip, scan or attachment. It should feel as if chat always worked this way.
  • The answer uses the exact names it read (get_lr(), line 39), which is the only confirmation, and makes a wrong guess obvious at once.

Edge cases

  • No scroll since your last message: use the pane that has keyboard focus.
  • A wrong guess: reply "no, the diff" and it answers again from that pane.
  • Code: read the visible lines with their file names and line numbers, so answers can cite them.
  • Privacy: nothing on screen is read until you press I, and only the chosen pane is read.

The prompt behind this film

ROLE
You are a motion designer and front-end engineer. Build a 50-second product launch film
as ONE self-contained HTML file that plays in a browser. It must feel like a real launch
video: one smooth virtual camera that zooms in and out of a desktop app, kinetic type,
and no web-page chrome inside the film.

PRODUCT
"Margin" is a chat assistant with a generic ChatGPT-like layout (sidebar, centered thread,
rounded composer). The product UI shows NO logo, avatar or name on answers. You type a
question normally and press Cmd+I instead of Enter. The context is the pane you scrolled
last, read as its visible text: an earlier answer in the same chat, a side chat, or a
code diff. The answer appears where you typed. Cmd+I leaves NO trace in the UI: no chip,
scan line, screenshot or attachment. The only confirmation is that the answer uses the
exact names it read (function name, file, line number).

STAGE AND CAMERA
- Author on a fixed 1920x1080 stage scaled to the container width.
- The desktop scene sits inside one ".camera" element; every zoom is a transform of it:
  shot(x, y, s) = translate(960 - x*s, 540 - y*s) scale(s), transform-origin 0 0.
- Scrolling is a translateY of each thread. Lay out every message up front (future ones
  at opacity 0) so scroll targets can be measured once and never shift.
- Film-only overlays (titles, captions, a small keystroke display, end card) live outside
  the camera. Draw the Command symbol as inline SVG; do not rely on a font glyph.
- Eases: power3.inOut for camera moves, expo.out for reveals. Zoom in for every typed
  question and every key moment; zoom out to full frame between scenes.
